The problem

Receipts arrive through email, chat, and manual uploads, and are easy to lose, duplicate, or acknowledge before the underlying record is durable.

An agent can coordinate bounded provider transport, duplicate checks, and host-file verification while leaving custody and accounting judgment with the selected backend and owner.

What you do

  1. Forward receipts to the configured mailbox or upload originals/screenshots in chat; the agent resolves workspace defaults.
  2. Start a manual or explicit external-trigger intake and choose IMAP, chat, or manual-upload evidence.
  3. Review one consolidated list of material exceptions; credentials belong only in Connections, while receipt uploads use the host chat attachment channel.

What the agent does

  1. Confirm the external workspace is readable and writable before any IMAP export.
  2. For IMAP, search a bounded candidate page, stage exactly one message, and validate the host handoff.
  3. Use the common external intake contract to deduplicate, atomically retain originals, update finance.json, and re-read the result.
  4. Only after verified external persistence, acknowledge the matching UIDVALIDITY/UID and clean up the staged transfer.

When this workflow helps

A reusable method, adapted to the request.

  • A receipt, invoice attachment, screenshot, or other evidence must enter the selected finance backend through the common intake protocol.
  • A dedicated receipt mailbox has a bounded candidate message that needs store-before-ack handling.

Before it starts

Depends on the selected path

  • An explicitly selected external backend and writable workspace
  • Host access to the selected workspace and the uploaded originals or IMAP staging route
  • A durable operator policy reference
  • A verified SSL or STARTTLS IMAP connection only when the IMAP route is selected

What proves it worked

Evidence, not a success claim.

  • Safe external receipt-record and host-write proof refs
  • Safe source identity and hash/path verification refs
  • Epoch-qualified acknowledgement and cleanup state when IMAP is selected

    Verified outcome

Safe stopping and recovery

Useful even when the whole path cannot run.

  • Stop after a staged candidate when host verification cannot proceed.
  • Stop after the external record is verified but before acknowledgement when the mailbox epoch or provider result is uncertain.
  • If the workspace, hashes, paths, or finance.json re-read fail, stop before acknowledgement and retain only a safe exception reference.
  • If acknowledgement is unknown or fails, preserve the verified external record and transfer id, then retry the same epoch-qualified acknowledgement without re-ingesting it.
