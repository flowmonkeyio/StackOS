## Blocking finding: escaped protected values are not guarded consistently across input, command and retention boundaries

The source-file admission path normalizes escapes before checking inherited protected values (`plugins/engineering/scripts/source_admission.py:23–61`). The general controller sanitizer does not: `plugins/engineering/scripts/delivery.py:175–184` checks only the raw value and its two canonical JSON serializations. Neither general labelled-secret redaction nor these exact replacements detect a different escape spelling of an otherwise unlabelled inherited value. Thus the required protection is still dependent on which route receives the text.

The following are concrete source-derived paths; the canary below is fabricated and no real credential was accessed or disclosed:

1. **Model prompts and retained requirements.** Assume the inherited protected value is the synthetic `DemoCanary123`. Ordinary requirement prose containing the literal characters `DemoCana\x72y123` has neither a secret-labelled assignment nor any of the three spellings searched by `_sanitize`. `_safe_text` at `delivery.py:192–195` therefore accepts it. The task-file entry point uses that check at `delivery.py:1264`, stores the task as the run-plan goal at `delivery.py:1344`, and `_prompt` includes it in each role's input at `delivery.py:564–593`. `_safe_role_prompt` returns immediately on the same insufficient check at `delivery.py:306–307`; the ordinary prose check at line 318 has the same limitation. The host receives that prompt at `reviewer_isolation.py:808–813`. Source admission is never invoked for this prose. The protected value's escaped representation consequently reaches model input and durable records.

2. **Decoded observation arguments.** `delivery.py:736` checks the serialized observation JSON before `json.loads`, then lines 739–756 validate only structure. A valid JSON argument spelled `"\u0044emoCanary123"` passes the pre-decode protected-value check and becomes the raw synthetic protected value after JSON decoding. There is no subsequent protected-value check on decoded fields. The resulting argument flows to unconfined execution at `delivery.py:836` or the confined observation adapter at `delivery.py:797`, whose `outcome_command` checks shape/size only before forwarding `argv` to `command/exec` (`reviewer_isolation.py:363–385`). This exposes the raw protected value in command arguments; eventual output redaction cannot undo that disclosure. Observation data also flows into run-plan inputs at `delivery.py:1346` without post-decode validation.

3. **Logs and ledger records.** The same incomplete `_sanitize` is used for stdout/stderr capture (`delivery.py:707–724`), dispatch-prompt retention (`delivery_recovery.py:188`), preparation-failure prompts (`delivery_recovery.py:900`), completed prompts (`delivery_recovery.py:1091`), and ledger validation (`delivery_recovery.py:150–154`). A string containing the noncanonical escaped canary remains unchanged at these boundaries. Passing the complete protected-value tuple privately to the broker does not repair these controller paths.

Required correction: apply one conservative protected-value policy consistently before disclosure/dispatch and before retention, including escaped spellings, and validate decoded structured input before using or saving it. Keep general prose/log handling strict; do not extend executable-source exemptions into prose. This is one boundary-consistency blocker with multiple affected paths, rather than a request to revive the stopped lexer approach. The inadequate general sanitizer predates this delta, but preserving strict inherited-value protection across these explicitly required boundaries is a condition of approval for this candidate.
