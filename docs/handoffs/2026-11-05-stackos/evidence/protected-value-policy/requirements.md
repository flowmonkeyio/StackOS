# Separate protected-value policy requirements

Authorized assignment: proceed with a separate protected-value policy implementation against the preserved pre-parser baseline, as a materially different bounded change. Preserve fail-closed behavior, independently review the identified boundaries, and run security/behavior checks only after logic approval. Do not alter or retry the held parser candidate. After acceptance, evaluate the separate source-admission integration and state what remains for a real safe run. No installation, business relaunch, push, merge, deployment, provider action, or managed-database mutation is authorized.

The implementation belongs only in `protected-value-policy-candidate`, branch `codex/protected-value-policy-20261105`. It starts with the original dirty four-session implementation preserved before the parser attempt. The previous candidate, parser snapshots, both rejection records, migration worktrees, active domain owners and all run/stop/retry history remain unchanged. No Acorn or source-expression admission exemption belongs in this change; current strict source rejection remains in force.

Required behavior:

1. Establish one explicit protected-value policy under the existing generic artifact/redaction owner, used consistently by the engineering controller and its trusted helpers. Capture the existing inherited protected-value set once per controller invocation; do not discover additional credentials, read authentication/session files, or expose protected values or derivatives in diagnostics, arguments, environment, model input or durable records. The policy is opt-in; unrelated consumers of existing label-based redaction retain their behavior.
2. Recognize raw and escaped representations of protected values, including partial JSON Unicode spellings and JavaScript hex/Unicode/identity/octal escapes, all line-continuation forms, escaped backslashes and surrogate pairs. Interpret original escape sequences without repeatedly decoding newly produced bytes. Explicitly bound inputs, normalization and structured traversal. Malformed or unsupported inputs must fail closed at the applicable boundary. Do not claim detection of arbitrary computed/encrypted encodings.
3. Reject unsafe requirements and assembled role prompts before saving or sending them. Validate structured values after decoding, including observation specifications, command arguments, tool arguments/results, model answers and retained metadata. Revalidate at the execution/disclosure boundary, including both confined and unconfined observations and model-requested outcome commands. Do not silently rewrite executable arguments or original source.
4. Apply the same known-value policy to source snapshots, old/current changed-source capture, broker source reads/writes and paths. Preserve existing general secret-label redaction and all strict source rejection. Source and prose remain separately scoped; no executable-source exception is added here.
5. Trusted helpers in every relevant mode (ordinary worker, reviewer and observation) must receive the same policy through a bounded private transport. It must not enter model-visible input, command argv/environment, logs, persisted host records or accessible files/descriptors. Close policy transport before child/model host startup. Preserve the existing no-network and filesystem isolation; no permission widening.
6. Gate command/tool results before returning them to the model; sanitizing them later in controller logs is insufficient. Sanitize progress/errors/receipts before retention and independently validate final durable payloads. Keep sufficient safe metadata to explain a hold. Preserve existing run-plan secret-key policy, immutable source/digests, exact role/model/thread identity, approval-before-test gating and bounded retry/stop budgets. Do not rewrite old run history.
7. Keep the change bounded to the shared policy and necessary engineering adapters/documentation. No unrelated cleanup, migrations or framework replacement. Existing dirty files are preserved. Record exact limitations and any integration problem rather than treating compilation, agent claims or passing tests alone as proof of complete delivery.

Required sequence: implementation first; fresh independent logic/security review of these requirements and actual source only, without an executor report; only after approval a fresh test session. Static syntax/lint checks are allowed before review. Tests and live parser/model/business execution are not. The existing two-failure approach stop and 15-minute no-outcome rule remain in force; preserved budgets must not reset on agent replacement.

Post-approval proof must exercise real decoded input and output boundaries with synthetic protected canaries, demonstrate rejection before execution/disclosure/retention, check private transport descriptor/environment/argv isolation, and confirm benign flow, model configuration, review gating and recovery history remain usable. Tests must identify candidate module paths and must not accidentally exercise the old installed copy. The known JavaScript snapshot hold is expected to remain: this policy-only change cannot establish source-admission or migration readiness.
