# Amazon S3 Connector Contract

Verified: 2026-07-26

This connector gives agents the same file-management capability categories as
the FTP connector where Amazon S3 has an honest equivalent. It is an object
storage connector for Amazon S3 general-purpose buckets only. It does not
pretend that prefixes are directories, that copy-and-delete is atomic, or that
deleting a current object removes historical versions.

## Scope and authentication

Provider and connector key: `aws-s3`. Public action refs use `utils.s3.*`.
The `aws-access-key` auth method stores `access_key_id`,
`secret_access_key`, and optional `session_token` as encrypted secret payload.
Safe account configuration contains only `bucket` and `region`.

One StackOS Account binds one bucket. StackOS does not require a bucket-owner
account id or add a separate owner condition to requests. AWS IAM and bucket policy
are the authorization boundary: if the explicit credential can access
the configured bucket, the connector can use it. Setup and account testing use
`HeadBucket`; they prove bucket reachability, not an inferred IAM permission
set. Permission verification is therefore `unavailable`/`provider_enforced`.

The daemon constructs a boto3 session and S3 client from
explicit daemon-held credentials and the saved region. It never falls through to environment
variables, shared AWS files, instance metadata, container credentials, or
another ambient credential chain. Temporary credentials with a session token
are recommended. Automatic STS assumption and credential renewal are not part
of v1.

Access key ids are treated as secrets even though AWS sometimes displays them
as identifiers. Credentials, session tokens, authorization headers, signed
URLs, canonical requests, and raw request bodies never enter action input,
output, metadata, errors, or audit records.

Least-privilege IAM remains operator-owned and should be limited to the bound
bucket and intended prefixes. Account testing and prefix listing need
`s3:ListBucket`; object reads and ETag-conditional deletes need `s3:GetObject`;
uploads and copy destinations need `s3:PutObject`; current-object deletion needs
`s3:DeleteObject`; and cleanup after an incomplete multipart operation needs
`s3:AbortMultipartUpload`. The connector never sends a version id for deletion,
so v1 does not require or exercise `s3:DeleteObjectVersion`. KMS-encrypted
objects can additionally require the applicable KMS permissions. StackOS does
not infer or broaden any of these grants.

## Executable action contract

| Action ref | Risk | Contract |
| --- | --- | --- |
| `utils.s3.directory.list` | read | Call `ListObjectsV2` for one exact optional prefix and delimiter. Return at most 1,000 object/common-prefix entries plus an opaque next cursor. |
| `utils.s3.file.upload` | write | Upload explicit local-file or local-directory mappings. Directory traversal preserves relative keys and creates zero-byte markers for empty directories. |
| `utils.s3.file.download` | write | Download explicit object or prefix mappings to exact local destinations. Each mapping declares `remote_kind=object|prefix`; the connector does not guess. |
| `utils.s3.file.delete` | write | Delete one exact current object key. Preserve returned version/delete-marker facts and never imply that historical versions were purged. |
| `utils.s3.directory.create` | write | Create one zero-byte trailing-slash object as a directory marker. It does not create a real directory or parent hierarchy. |
| `utils.s3.directory.delete` | write | With `recursive=false`, delete only the exact marker after proving no other current objects exist below the prefix. With `recursive=true`, page and delete the bounded current object set. |
| `utils.s3.path.rename` | write | Rename one exact current object by conditional copy followed by conditional source delete. It is non-atomic and reports copy/delete stages independently. |

Prefixes and object keys are provider-native inputs. The connector rejects NUL
and unsafe control characters, but it does not impose an FTP-style root or a
generated-assets allowlist. Prefix rename is not exposed. A source or
destination ending in `/` is therefore rejected by `path.rename` rather than
being interpreted as a tree move. The exact root object key `soap` is also
rejected because AWS requires path-style addressing for that one key while this
connector intentionally supports only virtual-hosted addressing. A listing
prefix of `soap` remains valid, but an exact returned `soap` object is marked
unsafe to reuse.

## Listing and directory markers

S3 has a flat key namespace. `directory.list` accepts `prefix`, optional
`delimiter`, `page_size` from 1 through 1,000, and an opaque continuation
cursor. It returns object entries and common-prefix entries separately, retains
safe size/ETag/storage-class/last-modified facts, and never auto-pages beyond the
requested page. Listing requests use S3's URL-encoding response mode and decode
keys exactly so XML-sensitive names cannot corrupt the provider response;
decoded keys that violate the connector's safe input contract are visible but
marked unsafe to reuse.

Directory creation writes only the normalized trailing-slash marker key with a
zero-byte body. The result says `marker_created=true`; it never claims a native
directory exists. Recursive directory operations operate on a normalized
trailing-slash prefix so `reports/` cannot match `reports-old`.

## Upload and download

Upload and download accept one or more explicit mappings plus
`conflict_policy=overwrite|skip|fail` and
`error_policy=stop|continue`. Upload also accepts
`follow_symlinks=false` by default. False reports symlinks as skipped. True
follows links under their link name with local ancestry-cycle detection. Upload
traversal is a preflight: the connector collects valid mappings and enforces the
global 10,000-object bound before the first provider mutation. With
`error_policy=continue`, a traversal failure is scoped to that top-level
mapping and later valid mappings still run; `stop` fails the preflight
immediately.

Small files use `PutObject`. Larger files use an explicit multipart lifecycle:
create, upload bounded parts, complete, and request one abort after a known
pre-completion failure. AWS can retain an in-flight part after a successful
abort response and recommends `ListParts` verification or repeated aborts.
StackOS v1 does not claim that this one-shot cleanup is verified: affected
receipts retain `cleanup_unverified=true`, the opaque upload id, safe abort
error/request facts, and reconciliation guidance. Upload parts start at 8 MiB
and grow before transfer when necessary to stay within S3's 10,000-part,
5 GiB-part, and 50,000 GiB (about 48.8 TiB) object limits. Multipart completion
is the visible write boundary. Conflict policies use conditional writes rather
than a check-then-write race:

- `overwrite` permits replacement of the current destination;
- `skip` and `fail` require destination absence with `If-None-Match: *`;
- a precondition conflict is reported as a known skip or failure, not retried as
  an unconditional write.

Downloads write to a sibling temporary file and publish with atomic
`os.replace`. Prefix downloads page the complete selected current-object set,
project every relative key under the chosen destination, reject traversal or
absolute projections, and create empty directories from markers. Failed
transfers remove their temporary files. Existing local destinations follow the
selected conflict policy.

## Delete and rename semantics

`file.delete` targets one exact current key. When a stable current ETag is
available or provided, the delete uses a matching condition. Results preserve
safe `VersionId` and `DeleteMarker` facts. In a versioned bucket, deleting
without a version id can create a delete marker while retaining prior object
versions; StackOS never labels this a historical purge.

`directory.delete` requires `recursive` and a positive `max_objects` bound.
Non-recursive mode lists enough to prove that no non-marker current object is
under the prefix, then deletes only the marker. Recursive mode inventories all
current keys under the exact normalized prefix before mutation. If the bound is
exceeded, it fails before deletion. General-purpose-bucket batch identities use
only `Key` plus the current `ETag`; directory-bucket-only `Size` and
`LastModifiedTime` conditions are never sent. It deletes bounded batches,
preserves each known success/error, and reports partial state and reconciliation
guidance. It does not enumerate or remove historical versions.

Rename is copy plus delete, not an S3 primitive. The connector heads the exact
source, uses its current version or ETag as the copy-source condition, applies
the selected destination conflict policy, then deletes the source with the
observed identity condition. `CopyObject` is used only through AWS's inclusive
5,000,000,000-byte limit; larger objects use bounded multipart copy. Copy parts
start at 64 MiB and grow before mutation when needed to remain within the
10,000-part provider limit. Copy success followed by delete failure returns a
partial result with both keys, `retry_safe=false`, and explicit reconciliation
guidance. StackOS never rolls back by blindly deleting the destination.

For a versioned source, the copy addresses the observed `VersionId`, but v1
deliberately deletes the current key without `VersionId` so it never purges a
historical version. The delete is ETag-conditional. A concurrent replacement
that receives the same ETag is therefore a narrow residual race: the copy can
contain the observed version while the current key later receives a delete
marker. The partial/non-atomic receipt and reconciliation guidance are the
operator boundary for that case.

## Errors, retries, output, and audit

Reads use the SDK's bounded standard retry policy. Mutations use a conservative
client configuration and are not blindly repeated by connector code. A
conditional conflict, explicit AWS error, transport failure, or ambiguous
post-send outcome becomes a structured `ActionConnectorError`.

Safe results and errors retain the AWS error code, HTTP status,
`x-amz-request-id`, extended request id when available, version id,
delete-marker state, continuation cursor, completed stages, partial item
effects, outcome certainty, retry safety, and reconciliation guidance.
Sensitive request material is redacted before shared action-call persistence.
Multipart failures also distinguish destination outcome uncertainty from
unverified retained-part cleanup; one accepted abort response is never described
as proof that all in-flight parts are gone.

Upload, download, recursive directory delete, and object rename use the shared
background action path. List, exact object delete, and directory-marker create
remain inline. Stored terminal action-call state is authoritative. A daemon
restart or ambiguous provider response never becomes inferred success.

## Deliberately excluded from v1

The connector is not a generic S3-compatible endpoint adapter. MinIO, R2,
DigitalOcean Spaces, custom endpoints, path-style compatibility switches,
directory buckets, access points, S3 on Outposts, Glacier restore orchestration,
presigned URL generation, object ACL management, bucket creation/policy,
cross-bucket copy, prefix rename, synchronization, historical-version purge,
Requester Pays headers, SSE-C key handling, MFA Delete, Object Lock governance
bypass, and automatic STS role assumption require separate contracts.

Mocked proof must cover explicit credential construction without ambient
credential fallback, manifest registration, account testing, no-secret output, list
cursor bounds, conditional conflicts, multipart completion/abort, recursive
local traversal, per-mapping upload continuation, global upload bounds, atomic
download placement, prefix containment, exact-`soap` rejection, directory
markers, bounded recursive delete, version/delete-marker receipts, decimal
5 GB copy routing, non-atomic rename partial failure, generic grant/audit
linkage, package inclusion, and provider presentation. A disposable live AWS
bucket remains operator-owned release evidence and is not simulated by the test
suite.
